# 在手机 Agent (Kimi 等) 里用豆哥配煤

> 给同事看的接入说明。不需要装任何东西，只要一个支持 MCP 的 App 和一把密钥。

## 1. 拿密钥

找管理员在后台「API 密钥」里生成一把，用途选 **手机 Agent (只读+求解)**，名字写你的名字
(如「李四-手机」)。密钥只显示一次，管理员当场发给你。

这把密钥**只能查和算**，改不了煤池、合同和煤库。丢了告诉管理员销毁重建即可。

## 2. 在 App 里添加 MCP 服务

| 项 | 填什么 |
|----|--------|
| 类型 | Streamable HTTP (有的 App 叫 "HTTP" / "远程") |
| 地址 | `https://doudou-blend.up.railway.app/mcp` |
| 请求头 | `Authorization: Bearer <你的密钥>` |

App 只让填一个地址、不能设请求头时，地址改填
`https://doudou-blend.up.railway.app/mcp/<你的密钥>` —— 这个地址本身就是密钥，别发群里。

## 3. 能做什么

直接用中文说就行，例如：

- 「按今天的合同算个配方」 → `today_blend`
- 「雪坪停了，不用它再算一次」 → `today_blend`，把雪坪放进 exclude (要完整煤名；一个词对应几种煤时逐个列出)
- 「明鑫 4 份、豹子沟 2 份、大佛寺工程煤 3 份，验算一下」 → `check_ratios`
- 「老母坡筛精是什么煤」 → `find_coal`
- 「现在合同要求是多少」 → `get_contract`

| 工具 | 作用 |
|------|------|
| `today_blend` | 按线上保存的合同与煤池，求最低成本配方：配比 (带煤种)、吨数 (按整铲配时带铲数)、每种煤估算价、成本、8 项指标体检 |
| `check_ratios` | 按给定配比验算成本与指标 |
| `find_coal` | 查煤：状态、是否参与今日求解 (不参与时说明原因)、煤种、产地、指标 (按煤池里改过的值，标出哪些是用户改过的、哪些是规格值)、质量指数与估算价 (对标的基准报价) |
| `get_contract` | 当前合同要求 (每项写明判定规则)、采购吨数、估价用的分煤种基准报价 |

### 结果怎么读

- **煤名要写全。** `exclude` 和 `check_ratios` 里有一个煤名对不上煤池里的煤，就不求解，回一段说明：
  没有叫「X」的煤，名字里带 X 的有哪几种 (没有近似的就提示用 `find_coal` 查)。比对时忽略大小写、
  首尾空格和全角空格，验算时按煤池里的写法去算。「本次排除」只列真正被拿掉的煤；点到了但本来就
  不参与求解的煤单独列出，每种煤写明原因 (没启用、隐藏、已停用、重名、数据非法)。
- **验算只用参与求解的煤。** `check_ratios` 的配比里点到在煤池里、但不参与求解的煤时不验算，直接说
  「X 在煤池里但不参与求解: 原因」，不算无解；名字对不上时列出的近似煤名也只含能参与求解的煤。
- **判定规则。** 合同每项有判定规则，例如「保留 1 位小数、截断后判定」：硫 1.0998 截成 1.0，合同
  ≤1 就算达标。合同项没写规则时，岩相按原值判，其余按 1 位小数截断判。`get_contract` 每项后面写明
  规则并举一个贴着合同界的例子；指标行同时给真实值和判定值，例如
  「硫 S 1.0998, 按合同规则记 1.0 (合同 ≤1): 达标 (原值超出合同数, 按合同判定规则算达标)·卡线」。
  真实值至少两位小数，位数不够区分结论时自动加位；加到 6 位还不够时不再四舍五入，改为朝判定那一侧
  截断 (如「水分 M 7.999999, 按合同规则记 7.9」，不会写成 8.000000)，所以照显示的数按规则判，结论总与
  判定值一致。判定值与真实值相同时不重复。
- **指标结论。** 「达标」= 按规则在界内；「不达标」= 越界；「界内 (估算值)」= 按规则在界内，但这个
  值是线性加权估算、未经实测校准 (挥发、粘结、胶质、岩相、CSR)；原值超出合同数、靠判定规则 (取舍或
  允许偏差) 才算过的，分别写「达标 (原值超出合同数, 按合同判定规则算达标)」和「界内 (估算值; 原值超出
  合同数, 按合同判定规则算界内)」；「无法判定」= 有参配煤缺这项数据；计价指标超合同界但没到拒收线时
  写明按条款扣多少 (估算的指标再注明估算值)；「合同无要求」= 这项合同没约束。「卡线」= 顶在界上。
- **两个 CSR。** 合同的焦炭强度 CSR 按指标行里的 CSR 值判定 (各煤 CSR 按配比加权；开了煤阶交互时
  再扣掉相应点数)。「捣固炼焦 CSR 估算」是按捣固公式由配合煤挥发、粘结、胶质另算的参考值，不参与
  达标判定；它低于合同下限时会点出来。
- **无解。** 每个卡住的指标一句话：合同要求多少，其余要求都满足时这批煤最好能做到多少，合同上这一项
  写成多少才配得出。最后这个数是「合同上要填的数」，系统已按这一项的判定规则和合同另允许的偏差逐档
  真解过，所以可能比「最好能做到」的值还松一侧 (截断规则下写 ≤1.2 实际放行到 1.2999；按原值判定、
  另允许超出 0.5 时写 ≤10.3 放行到 10.8)，两者并不矛盾，句子里会写明是哪条规则让它放宽。计价指标卡住
  的是拒收线，写成「拒收线 ≤X」「拒收线放宽到 ≤Y 才配得出」。给不出这个数时说明只放宽这一项不够。
  设了安全余量的会注明。
- **整铲。** 一铲最小量凑不成整铲时，配方列表正上方会写明「下面的吨数没有按整铲取整，不能直接照此
  装车」，这时不要照着吨数自己凑铲数。

## 4. 口径 (和网页今日屏一致)

- 合同、煤池 (启用/隐藏/改过的指标) 用网页上保存的那一份 —— 要换合同，在网页「合同」里改。
- 所有煤价都是**估算价**：按指标 (含挥发分，不先分煤种) 找最接近的几条**基准报价** (公开的出厂含税价与
  价格指数，带日期) 加权，各条按 1000 点质量指数之比换算 —— 估算价 = Σ 份额 × 基准价 × 本煤质量指数 ÷ 基准品质量指数。基准报价比焦煤现货
  指数最新一期旧时，按指数涨跌推算到今天。管理员可在后台「基准报价」补录新报价。估算价有误差，下单前要问实价。
- 已停用的煤 (停产、拉不出来) 不会进配方。数据非法 (缺指标表、偏好结构不对、化验值不是非负数) 或
  重名的煤也不进配方，结果的提示里会点名。煤池里某种煤的整条偏好坏了 (不是对象，含 null) 按数据非法
  算；自建煤缺名字、状态不认识或指标表不是对象的，网页不显示，这里也当它不存在 (不参与重名判断)。
- 网页的「采购扣款模板」只存在浏览器里，Agent 这边不计买入侧扣款，结果里会提示。

## 5. 给开发者

- 入口：`POST /mcp` (或 `/mcp/{key}`)，无状态 JSON-RPC，只回 JSON，`GET` 回 405。
- 鉴权：`data_api_keys` 里 `scope = 'mcp'` 的密钥；`data` 用途的密钥 (写煤库) 进不来，反之亦然。
- 请求组装：`blend_kit_server/src/today.rs`，规则对照前端 `domain/resolvedCoal.ts`；协议与排版：`src/mcp.rs`。
- 煤池解析两端共用一份用例 `blend_kit_server/data/pool_cases.json` (输入服务端存的偏好与自建煤、master
  片段 → 每种煤的状态、指标与用户改过的指标)，Rust (`today.rs` 的 `shared_pool_cases_match_fixture`) 与
  vitest (`doudou_blend/src/domain/resolvedCoal.parity.test.ts`) 各跑一遍。vitest 照网页真实路径走：
  先经 `initializeCloudStorage` 写进本地缓存，再由 `getCoalPrefs()` / `getUserCoals()` 读出后解析，
  所以存储层的归一化也在对照之内。改任何一端的煤池规则，先在这里加用例。
