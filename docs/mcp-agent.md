# 在手机 Agent (Kimi 等) 里用豆哥配煤

> 给同事看的接入说明。不需要装任何东西，只要一个支持 MCP 的 App 和一把密钥。

## 1. 拿密钥

找管理员在后台「API 密钥」里生成一把，用途选 **手机 Agent (查询+求解+询价存档)**，名字写你的名字
(如「李四-手机」)。密钥只显示一次，管理员当场发给你。

这把密钥**能查、能算，询价精算的报价会存档**；改不了煤池、合同和煤库。丢了告诉管理员销毁重建即可。

## 2. 在 App 里添加 MCP 服务

| 项 | 填什么 |
|----|--------|
| 类型 | Streamable HTTP (有的 App 叫 "HTTP" / "远程") |
| 地址 | `https://doudou-blend.up.railway.app/mcp` |
| 请求头 | `Authorization: Bearer <你的密钥>` |

App 只让填一个地址、不能设请求头时，地址改填
`https://doudou-blend.up.railway.app/mcp/<你的密钥>` —— 这个地址本身就是密钥，别发群里。

支持 Skill 的 Agent (Claude 等) 可以再装上仓库里的 `skills/doudou-blend/` —— 它只讲用法 (咨询四步、怎么把客户
的话翻成参数、哪些数只能当参考)，不含算法，数字仍全部由上面的 MCP 服务算。不支持 Skill 的 App (Kimi 等) 不用装：
同样的规矩已经写在 MCP 服务自带的说明里，接上就能读到。

## 3. 能做什么

直接用中文说就行，例如：

- 「按今天的合同算个配方」 → `today_blend`
- 「雪坪停了，不用它再算一次」 → `today_blend`，把雪坪放进 exclude (要完整煤名；一个词对应几种煤时逐个列出)
- 「这个客户硫要 0.8 以下、CSR 不低于 62，胶质不管，算一个」 → `today_blend`，
  specs 写 `{"S": {"max": 0.8}, "CSR": {"min": 62}, "Y": null}`
- 「他手上只有明鑫、豹子沟、大佛寺工程煤，就在这三种里配」 → `today_blend`，把三种煤的完整煤名放进 only
- 「明鑫 4 份、豹子沟 2 份、大佛寺工程煤 3 份，验算一下」 → `check_ratios`
- 「客户问回来了：明鑫出厂 1850、运费 60，豹子沟出厂 1720，按这个再算」 → `quote_blend`，
  quotes 写 `{"明鑫": {"fob": 1850, "frt": 60}, "豹子沟": {"fob": 1720}}`
- 「老母坡筛精是什么煤，最近涨了还是跌了」 → `find_coal`
- 「现在合同要求是多少」 → `get_contract`
- 「最近焦煤行情怎么样」 → `market`

给客户出配煤咨询答案按四步走：① 打分 (`find_coal` 查指标、质量指数与估算价) → ② 计算 (`today_blend`
按估算价求配方，客户的合同要求、候选煤用 specs / only 按次指定) → ③ 询价 (让客户去问配方里那几种煤的
实际出厂价与运费) → ④ 再计算 (`quote_blend` 按实际报价重算)。

| 工具 | 作用 |
|------|------|
| `today_blend` | 按线上保存的合同与煤池，求最低成本配方：配比 (带煤种)、吨数 (按整铲配时带铲数)、每种煤估算价、成本、8 项指标体检。可带 `specs` (本次合同要求)、`only` (本次候选煤)、`exclude` (本次不用的煤) |
| `check_ratios` | 按给定配比验算成本与指标。可带 `specs`、`only` |
| `quote_blend` | 询价精算：只用报了价的煤 (至少两种)，按到厂价 = 出厂价 + 运费求最低成本配方，并写出每种煤的报价比估算价高或低多少。可带 `specs`。这批报价会存档 |
| `find_coal` | 查煤：状态、是否参与今日求解 (不参与时说明原因)、煤种、产地、指标 (按煤池里改过的值，标出哪些是用户改过的、哪些是规格值)、质量指数与估算价 (对标的基准报价)；有每日估价快照的煤另带较前一日的涨跌与一周后的预测价 |
| `get_contract` | 当前合同要求 (每项写明判定规则)、采购吨数、估价用的分煤种基准报价 |
| `market` | 行情：钢铁网炼焦煤价格指数各品种 (综合指数在最前) 的最新值、较上一期的涨跌、一周后的预测 |

### 按次指定 (specs / only / quotes)

每个客户的合同、候选煤、报价都不一样，这三样都**只对这一次调用生效**，不改网页上保存的合同与煤池。

- **`specs` 本次合同要求** (`today_blend` / `check_ratios` / `quote_blend`)。在保存的合同上逐项覆盖，没提到的
  指标照旧。键为 `S` / `A` / `V` / `G` / `Y` / `petro` / `CSR` / `M`；只给 `max` 是上限，只给 `min` 是下限，
  两个都给是区间；写 `null` 表示本次不约束这一项。保存的合同里这一项的判定规则与安全余量照旧；原来是计价
  指标 (超了扣款) 的，本次按硬约束算，结果的提示里会写「本次按硬约束算, 未计扣款条款」；保存的合同里没有
  这一项就新建一条硬约束。写错 (不认识的指标、min 大于 max、不是数) 时不求解，回一段说明并列出可用的指标。
  结果第一行在合同名后面写明改了什么，例如「今日配方 (默认合同; 本次改: 硫 S ≤0.8、胶质 Y 不约束, …」。
- **`only` 本次候选煤** (`today_blend` / `check_ratios`)。只在点到的煤里配 (求最优至少两种)。煤池里没启用
  或隐藏的煤点到了也参与；已停用、重名、数据非法的不行，逐个说明原因。和 `exclude` 同时给时先取 only 再
  去掉 exclude。`check_ratios` 给了 only 时，配比里的煤必须都在 only 之内。结果里多一行
  「本次候选煤: …」。
- **`quotes` 报价** (`quote_blend`，必填)。完整煤名 → `{fob 出厂价, frt 运费 (可省), props 当场给的化验值 (可省)}`，
  单位元/吨。只用报了价的煤求解，煤池里没启用或隐藏的煤报了价也参与。运费没给按 0 计，结果的提示里点名
  (到厂价少算一截，配方会偏向这几种煤)。当场给的化验值只进这次计算与存档，不改煤池。报价写得不对
  (出厂价不是正数、超出合理范围、化验值非法、同一种煤写了两遍) 时不求解也不存档。

### 结果怎么读

- **煤名要写全。** `exclude`、`only`、`quotes` 和 `check_ratios` 里有一个煤名对不上煤池里的煤，就不求解，回一段说明：
  没有叫「X」的煤，名字里带 X 的有哪几种 (没有近似的就提示用 `find_coal` 查)。比对时忽略大小写、
  首尾空格和全角空格，验算时按煤池里的写法去算。「本次排除」只列真正被拿掉的煤；点到了但本来就
  不参与求解的煤单独列出，每种煤写明原因 (没启用、隐藏、已停用、重名、数据非法)。
- **验算只用参与求解的煤。** `check_ratios` 的配比里点到在煤池里、但不参与求解的煤时不验算，直接说
  「X 在煤池里但不参与求解: 原因」，不算无解；名字对不上时列出的近似煤名也只含能参与求解的煤。
  点到的是没启用或隐藏的煤时，说明末尾会提示把这次要用的煤名都列进 only —— 列进去就能验算。
- **判定规则。** 合同每项有判定规则，例如「保留 1 位小数、截断后判定」：硫 1.0998 截成 1.0，合同
  ≤1 就算达标。合同项没写规则时，岩相按原值判，其余按 1 位小数截断判。`get_contract` 每项后面写明
  规则并举一个贴着合同界的例子；指标行同时给真实值和判定值，例如
  「硫 S 1.0998, 按合同规则记 1.0 (合同 ≤1): 达标 (原值超出合同数, 按合同判定规则算达标)·卡线」。
  真实值至少两位小数，位数不够区分结论时自动加位；加到 6 位还不够时不再四舍五入，改为朝判定那一侧
  截断 (如「水分 M 7.999999, 按合同规则记 7.9」，不会写成 8.000000)，所以照显示的数按规则判，结论总与
  判定值一致。判定值与真实值相同时不重复。
- **指标结论。** 「达标」= 按规则在界内；「不达标」= 越界；「界内 (估算值)」= 按规则在界内，但这个
  值是线性加权估算、未经实测校准 (挥发、粘结、胶质、岩相、CSR)；原值超出合同数、靠判定规则 (取舍或
  允许偏差) 才算过的，分别写「达标 (原值超出合同数, 按合同判定规则算达标)」和「界内 (估算值; 原值超出
  合同数, 按合同判定规则算界内)」；「无法判定」= 有参配煤缺这项数据；计价指标超合同界但没到拒收线时
  写明按条款扣多少 (估算的指标再注明估算值)；「合同无要求」= 这项合同没约束。「卡线」= 顶在界上。
- **两个 CSR。** 合同的焦炭强度 CSR 按指标行里的 CSR 值判定 (各煤 CSR 按配比加权；开了煤阶交互时
  再扣掉相应点数)。「捣固炼焦 CSR 估算」是按捣固公式由配合煤挥发、粘结、胶质另算的参考值，不参与
  达标判定；它低于合同下限时会点出来。
- **无解。** 每个卡住的指标一句话：合同要求多少，其余要求都满足时这批煤最好能做到多少，合同上这一项
  写成多少才配得出。最后这个数是「合同上要填的数」，系统已按这一项的判定规则和合同另允许的偏差逐档
  真解过，所以可能比「最好能做到」的值还松一侧 (截断规则下写 ≤1.2 实际放行到 1.2999；按原值判定、
  另允许超出 0.5 时写 ≤10.3 放行到 10.8)，两者并不矛盾，句子里会写明是哪条规则让它放宽。计价指标卡住
  的是拒收线，写成「拒收线 ≤X」「拒收线放宽到 ≤Y 才配得出」。给不出这个数时说明只放宽这一项不够。
  设了安全余量的会注明。
- **整铲。** 一铲最小量凑不成整铲时，配方列表正上方会写明「下面的吨数没有按整铲取整，不能直接照此
  装车」，这时不要照着吨数自己凑铲数。
- **询价精算。** 第一行是「询价精算 (合同名, 吨数, 按你给的报价, 到厂价 = 出厂价 + 运费, …)」。配方里每种煤
  写「出厂报价 1850 元/吨 + 运费 60 = 到厂价 1910, 报价比估算出厂价 1795 高 55 元 (对标…)」；估算价对不上
  基准报价时不写后半句，不拿这批报价自己反推的价去评价报价。报了价但没进配方的煤单独列在「报了价但没进
  配方:」下面；无解时没有配方，改列「这次用的报价:」。结尾一行写明这批报价存没存成（存了写「这批报价已按批存档…」，
  没存成写明原因，不影响上面的结果）；同一请求里有多条询价精算时只存档最后一条算成的，其余在各自结尾说明；
  服务器忙或超时没算成的调用不存档。成本行的数按到厂价（含运费），与 `today_blend` 按估算出厂价的成本
  不能直接相减，成本行后面注明了这一点。
- **估价快照与预测。** `find_coal` 的「每日估价快照」一行是共享煤库每天存下的估算价、较前一日的涨跌
  (按显示出来的两个价之差，显示成同一个数写「持平」) 和一周后的预测价；你在煤池里改过指标的煤，行尾会注明
  快照不含你改过的值。`market` 每条指数一行，指数值保留 1 位小数，涨跌同样是显示值之差。预测按指数近期走势
  推算，行情拐头时会滞后，**只作参考，不进配方、不当报价，转告客户时要说明这只是参考**；预测的那天已经到了
  就不再显示。行情数据取不到时 `market` 回「行情数据暂时取不到」。

## 4. 口径 (和网页今日屏一致)

- 合同、煤池 (启用/隐藏/改过的指标) 用网页上保存的那一份 —— 要换合同，在网页「合同」里改。
- 所有煤价都是**估算价**：按指标 (含挥发分，不先分煤种) 找最接近的几条**基准报价** (公开的出厂含税价与
  价格指数，带日期) 加权，各条按 1000 点质量指数之比换算 —— 估算价 = Σ 份额 × 基准价 × 本煤质量指数 ÷ 基准品质量指数。基准报价比焦煤现货
  指数最新一期旧时，按指数涨跌推算到今天。管理员可在后台「基准报价」补录新报价。估算价有误差，下单前要问实价。
- 已停用的煤 (停产、拉不出来) 不会进配方。数据非法 (缺指标表、偏好结构不对、化验值不是非负数) 或
  重名的煤也不进配方，结果的提示里会点名。煤池里某种煤的整条偏好坏了 (不是对象，含 null) 按数据非法
  算；自建煤缺名字、状态不认识或指标表不是对象的，网页不显示，这里也当它不存在 (不参与重名判断)。
- 网页的「采购扣款模板」只存在浏览器里，Agent 这边不计买入侧扣款，结果里会提示。
- 询价精算与网页今日屏的「询价精算」同一口径：只用报了价的煤，按到厂价求解，估算价只作对照。报价按批
  存档到后台「询价对比」，供以后校准估价；存档的出厂估价由服务端按这批指标与当天基准重算，运费不进估价。
  同一天同一组煤再算一次，覆盖上一次的存档；换了煤或隔了天另起一批。无解也存档；服务器忙或超时没算成的
  调用不存档；存档失败不影响这次的结果，结尾一行会如实写明。报价不进煤池，也不跨次沿用。

## 5. 给开发者

- 入口：`POST /mcp` (或 `/mcp/{key}`)，无状态 JSON-RPC，只回 JSON，`GET` 回 405。
- 鉴权：`data_api_keys` 里 `scope = 'mcp'` 的密钥；`data` 用途的密钥 (写煤库) 进不来，反之亦然。
- 请求组装：`blend_kit_server/src/today.rs`，规则对照前端 `domain/resolvedCoal.ts`；按次覆盖 (specs / only /
  quotes) 在 `src/today_overrides.rs`，都不写存储。协议与排版：`src/mcp.rs`，行情与估价快照的排版在
  `src/mcp_market.rs`，询价精算在 `src/mcp_quote.rs`。这几个文件都不查库不联网，数据由 `lib.rs` 的
  `load_mcp_context` 装进 `Context` (估价快照与行情只在这批消息调了 `find_coal` / `market` 时才读)。
- 询价存档：`mcp::quote_archive` (纯函数) 由消息算出要存的那一批，`lib.rs` 在回包算完之后调
  `quotes::store` 落库 (与 `POST /api/quotes` 同一条路径；落库的 `quoted_on` 与批号同一天，取自
  `Context.today`)。批号是 `mcp-<北京时间 YYYYMMDD>-<归一化煤名排序后拼接的 SHA-256 前 16 位>`。
  只存档求解成功的调用 (回包是工具结果且工具没报错；闸门拒绝回的是 JSON-RPC error，不存)，一个请求最多
  存一批，取最后一条算成的；落库之后把「已存档 / 没存成」补到对应回包的文本结尾，失败另记日志。
- 求解闸门：`today_blend` / `check_ratios` / `quote_blend` / `find_coal` 要过计算闸门，`get_contract` 与
  `market` 不过。
- 煤池解析两端共用一份用例 `blend_kit_server/data/pool_cases.json` (输入服务端存的偏好与自建煤、master
  片段 → 每种煤的状态、指标与用户改过的指标)，Rust (`today.rs` 的 `shared_pool_cases_match_fixture`) 与
  vitest (`doudou_blend/src/domain/resolvedCoal.parity.test.ts`) 各跑一遍。vitest 照网页真实路径走：
  先经 `initializeCloudStorage` 写进本地缓存，再由 `getCoalPrefs()` / `getUserCoals()` 读出后解析，
  所以存储层的归一化也在对照之内。改任何一端的煤池规则，先在这里加用例。
